## Flujo

1. Obtener la cookie anónima y el token mediante `GET /api/v1/identidad/csrf`.
2. Enviar `POST /api/v1/identidad/recuperacion` con `correo` y la cabecera CSRF. El `202` sin cuerpo indica que se admitió la solicitud. El worker consulta la cuenta y envía únicamente a la dirección registrada y verificada de una cuenta habilitada.
3. La interfaz de recuperación recibe el comprobante en el fragmento del enlace HTTPS. Envía `POST /api/v1/identidad/recuperacion/confirmar` con `token`, `contrasena` y CSRF. La respuesta exitosa es `204`.
4. Volver a iniciar sesión por el flujo ordinario. Las sesiones anteriores se invalidan al recibir una solicitud posterior. El estado de empresas, membresías y atribuciones se mantiene.

El comprobante tiene 256 bits aleatorios y solo se guarda su huella SHA-256. La transacción de confirmación serializa por cuenta, verifica canal, vigencia y versión, actualiza la contraseña con el codificador existente, consume el comprobante e invalida otros enlaces vigentes. Los errores de comprobante válido en forma e inutilizable devuelven `409 RECUPERACION_NO_DISPONIBLE`. La respuesta no incluye datos de la cuenta.

## Activación en un entorno

Aplicar Flyway común V8 mediante el migrador técnico antes de desplegar esta versión. La autenticación consulta la versión de credencial aunque la recuperación esté deshabilitada. Para habilitar la recuperación, activar `mspi.recovery.enabled=true` y proporcionar las propiedades siguientes.

| Propiedad bajo `mspi.recovery` | Valor a configurar |
| --- | --- |
| `validity` | Vigencia positiva del comprobante |
| `reset-url` | URL HTTPS de la interfaz, sin credenciales, consulta ni fragmento |
| `from` | Remitente autorizado por el relay |
| `min-password-length` | Longitud mínima acordada. Usar la misma política que para las cuentas invitadas |
| `attempt-window` | Ventana positiva de solicitudes o confirmaciones |
| `attempts-per-key` | Tope por clave de correo para solicitudes o huella de comprobante para confirmaciones |
| `attempts-per-address` | Tope por dirección obtenida del contenedor |
| `total-attempts` | Tope por instancia que también acota los mapas de contadores |
| `concurrent-checks` | Máximo de confirmaciones simultáneas |
| `queue-capacity` | Capacidad de la cola local de entrega |

Los límites de solicitud y confirmación se cuentan por separado y se mantienen en memoria por instancia. El exceso devuelve `429`. La cola es acotada y local. El relay usa las propiedades `spring.mail` ya configuradas para SMTP con STARTTLS. Un fallo de envío revierte la emisión y deja solo un registro operativo con ID de correlación. Ante una interrupción del proceso se puede solicitar otro enlace. La interfaz, el relay real y los valores de operación requieren configuración de entorno. [Configuración SMTP](../INVITACIONES.md).
