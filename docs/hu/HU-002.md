Como equipo de desarrollo, quiero límites funcionales y contratos públicos verificables para construir el monolito sin ciclos ni acceso indebido a las implementaciones de otros módulos.

## Trazabilidad y alcance

ARQ-07, AT-02, APR-06 y APR-08, etapa 2. [Plan y rúbrica](../PLAN-HU-Y-RUBRICA.md) y [estructura y reglas](../ARQUITECTURA-MODULAR.md).

Incluye doce módulos cerrados, paquetes `api/internal`, listas explícitas de dependencias, verificación del modelo real y modelos de prueba que demuestran aceptación/rechazo. El workflow de HU-001 ejecuta las nuevas pruebas dentro de `clean verify` sin omitir la integración PostgreSQL existente.

Fuera de alcance: implementar los doce dominios, contratos de negocio sin caso de uso, migraciones, acceso multiesquema, sesión, API HTTP, frontend y documentación central. No se añaden dependencias Maven ni se cambian las versiones aprobadas.

## Decisiones de implementación

- Los límites usan `package-info.java` y anotaciones Modulith; las interfaces nombradas reservan `api`, sin inventar DTO o métodos de negocio.
- `gestion` puede consumir los once contratos `modulo::api`; los demás módulos no declaran consumidores hasta necesitarlos. Las dependencias concretas evolucionan con las HU que las requieran, manteniendo encapsulación y ausencia de ciclos.
- El modelo real usa la detección estándar de Modulith y excluye clases de prueba. Los modelos deliberadamente inválidos solo viven en `src/test/java/architecture/fixtures` y se importan explícitamente en sus pruebas.
- Se verifica el conjunto exacto de doce módulos para impedir un éxito vacío de `verify()` por una estructura no detectada. Una regla adicional protege los paquetes raíz que Modulith trataría como API implícita.

## Criterios de aceptación

- CA-01. El modelo real reconoce exactamente los doce límites aprobados, cerrados y con interfaz `api`.
- CA-02. `ApplicationModules.verify()` acepta el modelo real; los tipos ejecutables pertenecen a `api/internal`, salvo el arranque de la aplicación.
- CA-03. Un modelo aislado con dependencia explícita a una API pública supera la verificación.
- CA-04. Los modelos con ciclo, acceso a internos o dependencia no declarada fallan por violaciones de arquitectura, sin confundir un error de importación con un rechazo válido.
- CA-05. `clean verify` con Java 17 sigue arrancando el contexto con PostgreSQL real y empaqueta el JAR; los modelos de prueba no se incluyen en él.
- CA-06. CI ejecuta las siete pruebas (seis de arquitectura y una de arranque), sin fallos ni omitidas, y conserva reportes.
- CA-07. Estructura, dependencias, procedimiento de ampliación y límites documentados; PR exclusivamente hacia `Develop`.
