## API

Las rutas parten de `/api/v1/empresas/{empresaId}/activos`. AE, GS y AU pueden consultar el inventario. AE y GS pueden modificarlo con CSRF. El historial de un activo requiere AE según PER-38. RA queda fuera del inventario general.

| Método y sufijo | Operación |
| --- | --- |
| GET sin sufijo | Búsqueda literal por código o nombre con `texto` y filtros `estado`, `tipo` y `procesoId`. Paginación con `pagina` y `tamano` |
| POST sin sufijo | Alta con código, nombre, descripción, tipo, proceso y propietario. Custodio y ubicación opcionales |
| GET `/{activoId}` | Consulta local, incluidos archivados |
| PUT `/{activoId}` | Edición de datos básicos de un activo vigente con `revisionEsperada` |
| POST `/{activoId}/archivar` | Archivo con motivo y revisión vigente |
| POST `/{activoId}/restaurar` | Restauración con motivo y revisión vigente. Si una referencia dejó de estar disponible, indicar reemplazos locales y activos en `referencias` |
| GET `/{activoId}/historial` | Eventos paginados con actor, instante, motivo, correlación, campos modificados y referencias anteriores y nuevas cuando corresponda |

Se confirmó comparar códigos sin distinguir mayúsculas ni espacios en los extremos, conservando acentos y separadores. La clave usa Unicode NFC y mayúsculas independientes del idioma. El código visible se fija al crear, como decisión de implementación para conservar su reserva incluso después del archivo. Se confirmaron los siete tipos iniciales de DD-11, con códigos `INFORMACION`, `HARDWARE`, `SOFTWARE`, `SERVICIO`, `RECURSO_HUMANO`, `INSTALACION` y `RED`.

Las nuevas asignaciones requieren proceso y responsables activos en la misma empresa. Una edición puede conservar una relación histórica si quedó archivada después de asignarla. La restauración comprueba las referencias vigentes o sus reemplazos. El código, el UUID y el historial permanecen vinculados al activo. El inventario devuelve clasificación pendiente. C/I/D y datos personales corresponden a HU-015. La revisión de riesgos abiertos requiere el módulo de riesgos.

## Persistencia y actualización

La V3 empresarial añade inventario, unicidad por empresa, claves de pertenencia e historial de referencias. Las mutaciones y los eventos se guardan en la misma transacción. El runtime no tiene acceso directo de lectura a la tabla de auditoría. El historial usa una proyección local por activo y exige autorización en la API.

Para actualizar un esquema existente, suspender la empresa, esperar las operaciones en curso y ejecutar `upgrade <empresa-uuid>`. La reactivación por AP requiere V3 verificada. La prueba de actualización conserva un proceso existente en V2 tras el reintento. [Procedimiento técnico](../RECUPERACION-PREPARACION.md).
